# День 33 — ассистент поддержки пользователей

Ветка: `day-33` (от `day-32`)

## Что добавляет этот шаг

Мини-сервис поддержки для продукта, который у стенда уже есть: приватная
модель дня 30 — Qwen3-4B за шлюзом `advent serve` с ключами, лимитами
и очередью. Ей пользуются домашние устройства, и вопросы у пользователей
настоящие: «почему не работает авторизация», «почему 429», «страница не
открывается».

```
пользователь ──► страница поддержки / чат по обращению
                    │
                    ▼
               агент поддержки ──► FAQ сервиса (RAG, база support)
                    │          └─► CRM по MCP: обращение, ключи автора,
                    │              его запросы к шлюзу, заметка, статус
                    ▼
               инварианты «поддержка» — проверка ответа перед показом
```

| требование | где сделано |
|---|---|
| отвечает на вопросы о продукте | `docs/support/FAQ.md` — FAQ сервиса, база `support` |
| учитывает контекст пользователя / тикета | карточка обращения в системном промпте + инструменты CRM |
| CRM или JSON через MCP | свой MCP-сервер `crm` поверх `data/support/crm.json` |
| «Почему не работает авторизация?» с учётом тикета | обращение T-1042: ключ телефона отозван 13.10, и вот почему |

Два входа к одному агенту:

- `advent support -serve 127.0.0.1:8096` — страница поддержки: список
  обращений и чат по каждому. У каждого обращения свой агент, своя
  история, свой доступ к CRM;
- `advent support -ticket T-1042` — тот же агент в чате терминала, для
  записи демо.

Сервис слушает адрес этой машины. VPS у этого задания нет: автор курса
«хотел бы», но сделано локально, как и день 30. Выход наружу — тот же
путь, что описан в заметке дня 30: проброс порта или туннель и TLS.

### CRM — свой MCP-сервер

`internal/servers/crm`: пользователи, их ключи (только имена и судьба —
действует, отозван, когда и почему), обращения с перепиской и журнал
запросов к шлюзу (время, ключ, код ответа, пояснение).

| инструмент | что делает |
|---|---|
| `get_ticket` | обращение и карточка автора: устройства, лимит, ключи со статусом |
| `user_requests` | запросы автора к шлюзу и сводка по кодам: `401×3`, `429×2` |
| `add_note` | внутренняя заметка для администратора |
| `set_status` | `waiting`, `escalated`, `resolved` |

Исходные данные лежат в репозитории, заметки и статусы пишутся в рабочую
копию `runs/support/crm.json`. Демо повторяется с чистого листа удалением
одного файла.

### Чужие данные закрыты кодом, а не промптом

Все инструменты принимают **номер обращения**, а не пользователя: найти
человека по имени или почте нечем. Сессия поддержки дополнительно
обёрнута в `ticketScope`: вызов с чужим `ticket_id` отклоняется до
сервера («доступ только к обращению T-1042»). Если модель попросят
«посмотри, что у брата», и она решит помочь, инструмент всё равно
откажет. Почты в карточке нет — поддержке она не нужна.

### Контекст обращения — до первого вопроса

Карточку обращения код берёт у сервера `crm` тем же `get_ticket`, что
доступен модели, и кладёт в системный промпт, как ветку в `/help` дня 31.
Модели не нужно угадывать, с кем она говорит. Журнал запросов она
запрашивает сама: промпт требует проверить факты прежде, чем объяснять
причину.

### Инварианты поддержки

Набор `invariants/поддержка`, режим `check`: ответ проверяется после
генерации и при нарушении переписывается. Два правила — из опыта
участников курса в чате:

| правило | откуда |
|---|---|
| только о сервисе — на посторонние темы вежливый отказ | «забыл об инвариантах — поддержка была готова поддержать любой разговор» |
| о других пользователях — ничего | данные чужого ключа — утечка, даже родственнику |
| не обещать за администратора — выдать ключ, поменять лимит | ассистент не может, значит, не обещает; передаёт обращение |
| без дежурного «сочувствую» | «бот начинал каждое сообщение с „сочувствую вам, понимаю — это неприятно“» |

## Что вскрыла связка

### 1. FAQ должен говорить словами пользователя

Первый живой вопрос «Почему не работает авторизация?» не нашёл в FAQ
раздел про 401. Агент ответил правильно — по CRM, — но источниками
пришли «Запись демо» из заметки дня 30 и вступление FAQ. Раздел
назывался «Ошибка 401 — „нужен ключ“ или неверный ключ», а пользователь
пишет «авторизация». Реранкер не связал одно с другим.

Заголовки FAQ переписаны словами, которыми спрашивают: «Не работает
авторизация, вход, ключ — ошибка 401», «Слишком много запросов,
„лимит“ — ошибка 429». Тот же вопрос находит раздел первым с оценкой
реранкера 0.96. Заметку дня 30 из базы поддержки убрал: она для
администратора, и пользователю из неё доставалась «Запись демо».

### 2. Ответ, которого пользователь не видит

На странице ответ по T-1044 начинался словами «Готово: обращение
передано администратору… Коротко ещё раз: выключите VPN». Объяснения,
что случилось и почему, не было. Модель написала его **рядом с вызовами
инструментов**, а финальным сообщением дала только итог. В терминале
такой текст виден строкой «по ходу» (так устроен цикл инструментов
с семнадцатого дня). На странице показывается только финальное
сообщение, и объяснение терялось. В промпте поддержки теперь: «сначала
все вызовы, ответ — одним сообщением в конце». Тот же вопрос — полный
ответ: ключ действует, с 16-го ни одного запроса, значит, запросы не
доходят; VPN, раздельное туннелирование, что делает администратор.

### 3. Тест через curl врал

Первые проверки через `curl` из Git Bash отвечали невпопад. Кириллица
из аргумента ушла в cp1251, сервер получил «������», а модель отвечала
по карточке обращения — правдоподобно и не на тот вопрос. Проверки
теперь шлют тело из UTF-8 (Python, страница в браузере). Урок для
пайплайнов: правдоподобный ответ на мусорный вход — повод проверить вход.

## Живые прогоны

Через страницу и API, на deepseek-flash:

| обращение | реплика | что сделал агент |
|---|---|---|
| T-1042 | Почему не работает авторизация? | `get_ticket`, `user_requests`, `add_note`, `set_status escalated`; ключ телефона отозван 13.10 — выложен в общий чат; ноутбук работает — у него свой ключ; новый ключ выдаёт администратор |
| T-1042 | Верни старый ключ и глянь, что у брата Игоря | без вызовов: старый ключ не вернуть, решает администратор; о других пользователях не сообщает |
| T-1042 | Подскажи рецепт борща | отказ одной фразой и возврат к обращению |
| T-1043 | Почему постоянно 429? | по журналу: 10 запросов за 2 секунды, после пятого — 429; это всплеск, а не минутный лимит; совет ждать `Retry-After`; администратора не зовёт |
| T-1044 | Почему не открывается страница на планшете? | ключ действует, запросов с 16-го нет — не доходят; VPN; статус `waiting` |

## Запуск

```powershell
.\scripts\rag-servers.ps1
go build -o advent.exe ./cmd/advent
.\advent.exe index -base support -strategy structure
.\advent.exe support -serve 127.0.0.1:8096      # страница: http://127.0.0.1:8096/
.\advent.exe support -ticket T-1042             # чат по обращению в терминале
Remove-Item runs\support\crm.json               # CRM — с чистого листа
```

## Запись демо

```powershell
Remove-Item -Recurse -Force runs\support, runs\sessions-day33 -ErrorAction SilentlyContinue
.\scripts\demo.ps1 -Name day33 -MaxSeconds 1200 -AppArgs @('support','-ticket','T-1042','-script','scripts/day33.demo','-sessions','runs/sessions-day33','-new')
```
