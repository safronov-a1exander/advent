# День 34 — ассистент для работы с файлами проекта

Ветка: `day-34` (от `day-33`)

## Что добавляет этот шаг

`advent files "<цель>"` — ассистент, который сам работает с файлами:
находит нужные, читает, ищет по многим сразу, сравнивает и правит.
Задача ставится целью — «таблица в README отстаёт от заметок, обнови».
Команды «открой файл X» нет: какие файлы нужны, ассистент решает сам.

```
цель ──► агент ──► MCP files: list_files · read_file · search · write_file · edit_file
                        │                                    │
                        │                       правки ──► черновик runs/files/stage
                        ▼                                    │
                 отчёт: что прочитал,             diff ──► экран + reports/files/<время>.diff
                 что изменил, что на человеке                │
                                                  человек: advent files -apply
```

| требование | где сделано |
|---|---|
| читать файлы проекта | `read_file` — с номерами строк, кусками `from`/`to` |
| искать по нескольким файлам | `search` — регулярное выражение по шаблону путей, ответ `путь:строка: текст` |
| анализировать | цель → агент сам выбирает инструменты, до 24 кругов вызовов |
| создавать и изменять | `write_file` (новый файл или целиком), `edit_file` (фрагмент → замена) |
| минимум 2 сценария | обновить документацию по изменениям; проверить файлы на соответствие правилу |
| 2–3 файла | README и девять заметок; `main.go` и README |
| изменения как diff | diff черновика на экране и в `reports/files/` |
| воспроизводимо | каждая цель начинается с чистого черновика; та же цель — тот же прогон |

### Опасные операции — только через человека

Правило лекции — «удаление, git push, конфиги требуют подтверждения» —
здесь выполняет код, а не промпт.

- **Правки ложатся в черновик.** `write_file` и `edit_file` пишут
  в `runs/files/stage/<путь>`. Модель читает свои правки, будто они
  уже сделаны, а проект не тронут. Проект меняет только
  `advent files -apply`, и его запускает человек, посмотрев diff.
- **Удаления нет вовсе.** Инструмента нет — нет и риска.
- **Песочница путей.** Абсолютные пути, `..`, `.git`, `.env`,
  `config.local.yaml`, `keys.txt`, `runs/`, `index/` закрыты и для чтения,
  и для поиска: ключ не утечёт даже в результате `search`.
- **Правка точечная.** `edit_file` требует фрагмент, который встречается
  в файле ровно один раз. Не нашёлся — «перечитай и скопируй дословно».
  Нашёлся дважды — «возьми больше строк вокруг». Модель не может
  заменить «не то вхождение».

## Что вскрыли прогоны

### 1. Восьми кругов инструментов мало

Первый прогон «таблица в README отстаёт» сделал всю работу, кроме самой
работы: прочитал README и восемь заметок, нашёл расхождения, составил
правильные строки — и упёрся в лимит. С семнадцатого дня на ход даётся
8 кругов вызовов, и до записи дело не дошло. Ответ модели честно
кончался словами «правки не вносил — лимит инструментов закончился»
и строками, которые она собиралась вставить.

Лимит стал полем агента `max_tool_rounds`. У ассистента по файлам — 24.
Второй прогон: 14 вызовов модели, 24 инструмента, точечный diff —
цепочка веток и восемь строк таблицы, $0.017.

### 2. Цена занижалась в разы

Итог прогона печатался по `Reply.Usage()` и показал «вызовов модели 1,
in 38 828, $0.013». Цикл инструментов кладёт в `Reply.Steps` только
последний вызов, а промежуточные круги — нет. Настоящий расход — по
счётчику пула: 14 вызовов, 335 567 входных токенов (почти все — из кэша
провайдера, поэтому всего $0.017).

### 3. Проверка «по памяти» неточна

Сценарий проверки: «каждая ли команда из `main.go` описана в README».
Первый ответ нашёл 4 из 9 отсутствующих команд, ещё 4 записал в «спорные»,
`version` пропустил. При этом писал «поиск подстроки ничего не даёт»,
хотя `search` ни разу не вызвал: проверял на глаз, по прочитанному.

В промпт добавлено правило: наличие проверять `search` по каждому
элементу, в отчёт — только подтверждённое поиском. Второй ответ — все
девять (`demo`, `run`, `bench`, `serve`, `load`, `dev`, `review`,
`support`, `files`, `version`) с файлом и строкой объявления, и честная
оговорка про `retrieval`: она упомянута в тексте таблицы, но не как
команда. Совпадает с проверкой `grep` по README.

### 4. Ассистент видит больше, чем просили, и не лезет

На цели «обнови таблицу шагов» он сам заметил, что вводный абзац README
доведён до дня 21, таблица параметров — до дня 25, а в дереве каталогов
нет `internal/gateway` и новых серверов. Трогать не стал: «выходит за
рамки поставленной задачи», — и вынес это в «осталось на человеке».

## Запись

Три запуска подряд, как в жизни: цель → человек смотрит diff и применяет →
проверка.

1. «Таблица шагов в README отстаёт…» — 10 вызовов модели, 18 инструментов,
   /usr/bin/bash.015, 23 с. Diff: звено цепочки веток и девять строк — дни 26–34.
   Строка дня 34 появилась потому, что эта заметка уже лежала в
   : ассистент берёт дни из файлов, а не из промпта.
2.  — черновик перенесён в README и очищен.
3. «Проверь, что каждая команда описана в README» — 8 вызовов,
   9 инструментов, /usr/bin/bash.007. До применения таких команд было девять. После —
   две,  и : новые строки таблицы упоминают ,
   , , , . Проверка видит то, что сделала
   правка минуту назад, — по поиску в файле, а не по памяти.

Правка README из записи закоммичена как есть: это работа ассистента,
принятая человеком.

## Код

| файл | что там |
|---|---|
| `internal/servers/files/files.go` | MCP-сервер files: пять инструментов, черновик, песочница путей |
| `cmd/advent/day34.go` | `advent files`: цель, ход агента в консоли, diff черновика, `-apply`, `-diff` |
| `internal/agent` | `max_tool_rounds` — свой лимит кругов инструментов у агента |

## Запуск

```powershell
.\advent.exe files "Таблица шагов в README отстаёт от заметок в docs/days. Обнови её."
.\advent.exe files -diff        # ещё раз посмотреть черновик
.\advent.exe files -apply       # перенести черновик в проект
.\advent.exe files "Проверь, что каждая команда из cmd/advent/main.go описана в README. Файлы не меняй."
```
