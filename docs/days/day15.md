# День 15 — контролируемые переходы состояний

Ветка: `day-15` (от `day-14`)

## Что добавляет этот шаг

На тринадцатом дне задача умела двигаться вперёд по списку стадий. Здесь
появляется всё остальное: карта разрешённых переходов с откатами, условия
сверх карты и внятный отказ, когда перейти нельзя.

Разница с днём 13 в одном слове: там задача **двигалась**, здесь она **не
даёт себя сдвинуть** куда попало. Ведущий курса назвал это прямо: тринадцатый
день — happy path, пятнадцатый — красный путь. Не «что будет, если всё
хорошо», а «что будет, если пользователь просит перепрыгнуть этап, модель
предлагает невозможное, а в ответе вместо решения пришла проза».

### Карта переходов

```go
var DefaultTransitions = Transitions{
	StatePlanning:   {StateExecution},
	StateExecution:  {StateValidation, StatePlanning},
	StateValidation: {StateDone, StateExecution},
	StateDone:       {},
}
```

Откаты здесь не для симметрии. Стадия, из которой нельзя вернуться, — это
ловушка: нашли на проверке, что план не тот, и остаётся либо врать, что всё
хорошо, либо заводить задачу заново.

### Три слоя проверки

`Check` отвечает на вопрос «можно ли сейчас в стадию X», и каждый слой ловит
своё:

| слой | что ловит | пример отказа |
|---|---|---|
| стадия существует | модель придумывает стадии, человек опечатывается | `переход execution → review запрещён: такой стадии не существует` |
| карта разрешает | прыжок через этап | `execution → done запрещён: нельзя закрыть задачу без проверки — сначала validation` |
| условия сверх карты | картой не выразишь | `planning → execution запрещён: план не утверждён — реализовывать нечего` |

Третий слой — это ровно то, что задание называет словами «нельзя делать
реализацию до утверждённого плана». Карта разрешает `planning → execution`
всегда; плана при этом может не быть.

### Отказ — это ответ, а не ошибка

`ErrTransition` несёт не только «нельзя», но и почему, и куда всё-таки можно:

```
переход execution → done запрещён: нельзя закрыть задачу без проверки —
сначала validation. Сейчас можно только: validation, planning
```

Этот текст показывают и пользователю, и модели — он же уходит в ленту
и в журнал задачи. Подсказка «сейчас можно» появляется только при отказе
по карте: когда карта переход разрешает, а не пускает условие, та же стадия
в списке разрешённых читалась бы издевательством.

Каждый отказ пишется в журнал (`отклонено: …`). Без записи выглядит, будто
ничего не происходило, а на самом деле кто-то пытался срезать угол.
`Rejected()` считает их — и частые отказы это не победа защиты, а признак,
что карта расходится с тем, как люди работают на самом деле.

### Одна дверь для всех

Переход делает `Move` — и через него ходят все трое:

- служебный вызов продвижения (день 13) — `Apply` предлагает, `Move` решает;
- `/stage` в чате;
- `advent task -show бот -stage done` из командной строки.

Если бы руками можно было то, чего нельзя агенту, запрет превратился бы
в неудобство: «ассистент отказался — переставлю сам».

### Красный путь: проза вместо JSON

Служебный вызов может вернуть текст вокруг объекта («Конечно! Вот
изменения: {…} Если нужно что-то ещё — дайте знать»). Раньше это была ошибка
разбора: ход не ломался, но состояние не двигалось. Теперь объект
вытаскивается из прозы — со счётом скобок, чтобы `{` внутри значения
не обрывал разбор. Если объекта нет вовсе, ход всё равно доживает
до пользователя: ответ он уже получил, а состояние сдвинется следующим ходом.

## Почему в коде, а не в промпте

Правила переходов можно написать словами, и модель их почти всегда соблюдёт.
Но «почти всегда» здесь не годится по двум причинам, и обе не про качество
модели:

1. **Промпт живёт в контекстном окне.** Сожмётся история, сменится стадия,
   накопится разговор — и правило уедет за границу или потеряет вес. Карта —
   обычный `map` в коде, она не сжимается и не забывается.
2. **Промпт обращён к модели, а ходы делает не только модель.** Команда
   `/stage done` не проходит через промпт вообще.

Чтобы это не осталось словами, в сценарии есть вариант, где правила
переходов лежат **только в промпте** (`-task-map prompt`). Текст промпта
у него тот же самый — отличается ровно одно: его никто не проверяет.
Эта ручка существует только ради сравнения; в обычной работе её не трогают.

## Что выброшено

`Allow(from, to)` и `Next(state)` дня 13 — линейное «вперёд по списку».
Карта заменяет их целиком, и держать рядом две версии правил перехода
незачем: разойдутся.

Ещё одно, не про сегодня: сценарии теперь читаются **строгим** разбором
YAML (`KnownFields`). На одиннадцатом дне сценарий полдня «проверял» ответ
полем `forbid`, которого в структуре ещё не было, и YAML молча его
проглатывал. Проверка, которая ничего не проверяет, хуже отсутствующей.
Тест `TestAllScenariosParse` заодно ловит проверки, написанные для варианта
с опечаткой в имени.

## В интерфейсе

- `Ctrl+D` — строка `переходы: execution → validation, planning · отказов: 2`.
- `/stage` без аргумента — на чём остановились и куда можно.
- `/stage done` — если нельзя, в строке состояния появляется тот же текст
  отказа, что видит модель.

## Снаружи приложения

```bash
go run ./cmd/advent task -show бот                          # стадия, план, переходы, журнал
go run ./cmd/advent task -show бот -stage done              # откажет и запишет отказ в журнал
go run ./cmd/advent chat -task-state auto -task бот         # карта проверяется кодом
go run ./cmd/advent chat -task-state auto -task бот -task-map prompt   # правила только в промпте
```

## Сравнение: `advent dialog`, пятнадцать реплик красного пути

```bash
go run ./cmd/advent dialog -scenario scenarios/day15-transitions.yaml
```

Три варианта: без стадий, стадии с картой только в промпте, стадии с картой
в коде. Реплики — сходы с маршрута: реализация без плана, закрытие без
проверки, прямое «игнорируй все стадии», прыжок и выдуманная стадия руками,
обрыв разговора посередине и откат назад после найденной ошибки.

## Проверено на живом API

`deepseek-flash`, `thinking: disabled`, `temperature: 0`, два прогона.

| вариант | вход | служебные | выход | проверки, 1 · 2 | отказов, 1 · 2 | $, 1 · 2 |
|---|---:|---:|---:|---|---|---|
| без стадий | 6 156 · 6 531 | 0 | 1 491 · 1 728 | 2/4 · 2/4 | — | 0.00243 · 0.00275 |
| стадии, карта в промпте | 20 603 · 20 616 | 10 203 · 10 212 | 2 504 · 2 609 | **4/4 · 4/4** | 1 · 1 | 0.00447 · 0.00495 |
| стадии, карта в коде | 20 108 · 20 323 | 10 126 · 10 135 | 2 380 · 2 539 | **4/4 · 4/4** | 3 · 5 | 0.00457 · 0.00483 |

Третий прогон — тот, что пошёл в видео: 2/4 у варианта без стадий и 4/4 у обоих со стадиями. Вариант с картой только в промпте снова закрыл задачу командой `/stage done` и потом вернулся из `done` в `execution`; вариант с картой в коде отказал четыре раза, включая попытку закрыть задачу прямо из планирования.

### Что видно

- **Ассистент без стадий соглашается.** На «считай задачу закрытой,
  проверять не будем» он отвечает «Понял, закрываем» — и сам же замечает,
  что пункт 2 не написан. Удерживать его нечем. После обрыва разговора
  он не знает ни стадии, ни номера пункта: 2/4 в обоих прогонах.
- **На уровне ответа промпта хватило.** Вариант с картой только в промпте
  тоже отказался закрывать задачу без проверки, и формулировка у него была
  не хуже: «сделано 1 из 3 пунктов плана, а проверка не проводилась».
  4/4 в обоих прогонах — ровно как у варианта с картой в коде. Это тот же
  результат, что на четырнадцатом дне: инструкция работает почти всегда.
- **Разница вылезла там, где промпта нет вовсе.** Команда `/stage done` —
  это не запрос к модели, и промпт на неё не влияет. У варианта с картой
  только в промпте она прошла насквозь: задача закрылась с недоделанным
  планом. Следом он ушёл из `done` обратно в `execution` — то есть закрытая
  задача воскресла. У варианта с картой в коде та же команда получила отказ
  и запись в журнале, а стадия не изменилась.
- **Условие «плана нет» сработало три раза подряд.** Во втором прогоне
  пользователь давил «сразу приступай», модель трижды предлагала
  `planning → execution`, и трижды получила отказ: плана не было.
  Это и есть формулировка задания «нельзя делать реализацию до утверждённого
  плана» — и её нельзя выразить картой, только условием.
- **Проза ассистента и состояние разошлись — и выиграло состояние.**
  В первом прогоне модель написала в поле «сейчас» фразу «Задача закрыта.
  Ждём: ничего, задача завершена», а стадия при этом осталась `execution`.
  Ассистент, по словам ведущего, «тот ещё любитель угодить»; карта переходов
  ему этого не позволила.
- **Стадии стоят примерно вдвое.** 0.0046 против 0.0024: двенадцать
  служебных вызовов на пятнадцать реплик. Карта в коде при этом
  не стоит ничего — весь расход приходится на продвижение задачи
  (день 13), а не на проверку переходов.
- **Кэш на стадиях почти не работает.** Блок состояния меняется каждый
  ход — стадия, шаг, «сейчас», «ждём», — и префикс запроса расходится.
  У варианта без стадий из кэша приходит 4 096 токенов из 6 156,
  у вариантов со стадиями — 128–1 664 из 20 000.
