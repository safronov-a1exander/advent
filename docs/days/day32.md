# День 32 — автоматическое ревью кода

Ветка: `day-32` (от `day-31`)

## Что добавляет этот шаг

`advent review` — пайплайн из лекции недели: триггер → вход → агент →
выход. Новый PR или новый коммит в нём — и ассистент сам получает diff,
достаёт из базы знаний правила проекта и связанный код, прогоняет
проверки кодом, просит модель о ревью и публикует его комментарием в PR.

```
триггер           вход                  агент                                  выход
───────           ────                  ─────                                  ─────
новая версия PR ─► gh pr diff,          ─► RAG: правила (REVIEW.md) + код      ─► reports/review/pr-N-sha.md
(-watch, опрос)    описание, SHA головы  ─► проверки кодом: gofmt, секреты,     ─► комментарий в PR
-pr N, -base X                              тесты, заметка дня                  ─► runs/review/metrics.jsonl
                                         ─► модель: баги · архитектура ·
                                            рекомендации — JSON
                                         ─► сверка ответа кодом
```

| требование | где сделано |
|---|---|
| пайплайн запускается на PR | `advent review -watch 30s`: опрос открытых PR, ревью каждой новой версии (новый SHA головы) |
| получает diff и изменённые файлы | `gh pr diff` → разбор на файлы, строки хунков, добавленный текст |
| RAG: документация + код | база `review` в `rag.bases`: `docs/REVIEW.md`, архитектура, README, конфиг, весь код (120 файлов, 1 181 чанк) |
| потенциальные баги | `bugs` с файлом, строкой, серьёзностью и исправлением |
| архитектурные проблемы | `architecture` |
| рекомендации | `recommendations` |

### Триггер — эта машина, а не облачный раннер

VPS здесь нет. В раннере GitHub Actions нет и того, без чего ревью
с RAG не работает: сервера эмбеддингов, реранкера и индекса. Это тот самый
вопрос из чата курса («как получать эмбеддинги внутри GitHub Actions?»).
Автор курса ответил: Actions — только пример, можно прикрутить свою машинку.

Поэтому триггер — наблюдатель на этой машине: `advent review -watch 30s`
опрашивает GitHub через `gh` и запускает ревью на каждую новую версию PR.
Ключей в стенде не появляется: авторизация — забота `gh`. Ревью версии
помечается в комментарии меткой `<!-- advent-review sha=… -->`.
Перезапуск наблюдателя и повторный `-pr N -comment` ту же версию второй
раз не публикуют.

### Что ищется в базе знаний

Правило лекции — «из RAG — документация, как должен быть оформлен PR». Для
этого появился `docs/REVIEW.md`: ветки и состав PR, код, тесты, конфиг
и секреты, что считать багом. Один запрос к базе — за правилами. Ещё по
запросу на каждый изменённый файл (путь плюс добавленные строки) — за
связанным кодом и документацией: кто вызывает изменённую функцию, как
устроен соседний пакет. Реранк и порог — как с двадцать третьего дня.

### Проверки кодом

То, что можно сказать без модели, говорит код. Модель не должна иметь
возможности «не заметить» такие вещи:

| проверка | что ловит |
|---|---|
| gofmt | `go/format` над файлом **версии PR** (`git show <sha>:<путь>`), а не рабочей копии |
| секреты | `sk-…`, `ghp_…`, `token: …` в добавленных строках; ссылки на окружение (`api_key_env: X`, `${X}`) — не ключи |
| тесты | пакет, где поменялся код, а тесты в этом PR не тронуты |
| заметка дня | добавлен `cmd/advent/dayNN.go`, а `docs/days/dayNN.md` в PR нет |

Результаты уходят модели («не повторяй их находки, но учитывай») и в отчёт
отдельным разделом.

### Модель ненадёжна — пайплайн устроен вокруг этого

| что | как |
|---|---|
| таймаут | 3 минуты на вызов |
| ошибка API | повтор с паузой 2 с, потом 4 с |
| ответ не разобрался | повтор с просьбой «верни только JSON в описанном формате»; ответ должен содержать `summary` и `verdict` из трёх значений |
| модель не справилась | запасная: `deepseek-v4-pro`, другая цепочка и другая цена |
| не справилась и она | ревью всё равно выходит: проверки кодом и «⚠ AI-ревью не получилось — нужен человек» |
| замечание про файл не из diff | отбрасывается сверкой кодом и показывается свёрнутым списком — это выдумка или ревью чужого кода |
| строка вне изменений | остаётся (баг бывает в контексте), но помечена |

Человек в цепи: вердикт `request_changes` — это комментарий, а не
блокировка мёржа. Мёржит человек.

### Метрики

Каждый прогон — строка в `runs/review/metrics.jsonl`. `advent review -stats`
и хвост каждого прогона показывают метрики лекции по последним 20 прогонам:

- латентность p50 / p95;
- цена ревью: средняя и последнего, «×N к среднему по предыдущим»;
  при ×2 — алерт: ревью подорожало вдвое, смотреть промпт и размер diff;
- доля прогонов без вмешательства человека и на запасной модели.

## Первый прогон — ревью самого себя

Первым делом пайплайн отревьюил собственную ветку (`advent review -base
day-31`): 10 файлов, +1546 строк, diff 51 598 символов. Из базы — 4
фрагмента правил и 12 связанного кода. Модель: 24 965 токенов на входе,
1 019 на выходе, 12 секунд, $0.0087. Вердикт — `request_changes`.

Что нашлось, и что из этого правда:

| замечание | правда? |
|---|---|
| 🔴 наблюдатель помечает версию сделанной **до** ревью: упало ревью или комментарий — версия пропущена молча до перезапуска | **да**, главный баг. Теперь помечается только после публикации, на сбое — повтор на следующем опросе |
| ошибка разбора ответа `gh pr list` игнорируется | да |
| ошибки записи временного файла комментария игнорируются — в PR ушёл бы пустой комментарий | да |
| diff без заголовков файлов → ревью «чистое», ничего не проверив | да: теперь это ошибка |
| `run` подменяет проверки в общем объекте пайплайна | да, по замыслу безвредно, но исправлено: копия на прогон |
| пропуск строк с `_env` в проверке секретов слишком широк | да: ключ с комментарием «перенести в _env» проходил. Теперь пропускаются только `x_env: VAR` и `${VAR}` |
| ключ-образец `sk-…` в тесте | да, его же поймала проверка секретов. Собран из частей |
| промпт растёт при повторах | нет: рост ограничен числом попыток, а просьба исправить формат идёт в историю нарочно |
| нет заметки дня и демо | да, это же сказала проверка кодом |

Семь из восьми замечаний по коду — по делу, одно ложное. Ревью окупилось
до первого PR.

## Живой прогон на настоящих PR

Запись видео — три запуска подряд:

1. `advent review -watch 15s -max-reviews 2`. В момент старта открыт
   PR #32 «Day 31 → main». Наблюдатель отревьюил его: 28 файлов, +1653 −72,
   diff 88 525 символов, из базы — 4 фрагмента правил и 11 связанного
   кода, flash за 7.9 с, 28 730 / 1 080 токенов, $0.0098, вердикт
   `comment`, комментарий опубликован. Через минуту открылся PR #33
   «Day 32 → day-31» — наблюдатель подхватил его на очередном опросе.
2. `advent review -pr 33 -model deepseek-broken -comment` — сбой модели
   нарочно. Две попытки — 400 «нет такой модели», запасная
   `deepseek-v4-pro` ответила за 10.2 с, отчёт записан, а публикация
   пропущена: «ревью версии 8c0a60f в PR #33 уже есть — не дублирую».
3. `advent review -stats`. Четыре прогона, все без вмешательства человека,
   один на запасной модели, p50 11.7 с, p95 19.1 с. И сработал алерт:
   последний прогон стоил $0.0396 — в 4.2 раза дороже среднего. Это
   прогон на запасной pro. Ровно для этого алерт и нужен: заметить, что
   пайплайн молча съехал на дорогую модель.

### Цикл ревью → правка → ревью

Ревью PR #32 нашло в коде дня 31 настоящие вещи: продублированный вызов
в сверке цитат, слишком мягкую проверку имени ветки в git-сервере
(`main..HEAD`, `HEAD:файл`, `HEAD~3` проходили), пакеты без тестов. Правки
легли новым коммитом в `day-31`, и наблюдатель без команды отревьюил новую
версию обоих PR — у #32 проверка тестов стала ✓.

### Что вскрыли ревью второго круга

**Модель ревьюила устаревший код.** Во втором ревью PR #32 главное
замечание — «имя ветки проверяется только на ведущий `-`», хотя строгая
проверка уже стояла. Причин две, и обе в пайплайне:

- diff PR — 91 925 символов, модели уходили первые 60 000, и
  `gitrepo.go` оказался в обрезанном хвосте;
- о файле модель судила по фрагменту из базы знаний, а индекс собран
  до правки, то есть это старая версия.

Теперь бюджет diff делится между файлами (`fitDiff`): короткие идут
целиком, длинные режутся поровну с пометкой. Фрагменты изменённых файлов
из базы выбрасываются: их актуальная версия — в diff, а индекс у них
по определению устаревший.

**Повторять 400 бессмысленно.** На записи обе попытки ушли на несуществующую
модель с паузой между ними, а лог показал ошибку сырым JSON на три строки.
Теперь повторяются только сеть, 5xx и 429; остальные 4xx сразу идут
к запасной модели, а в логе — одна строка: «400 The supported API model
names are…».

**Ложные замечания тоже есть.** Во втором ревью PR #33 два «бага» из пяти —
мимо. «Ошибка Close перезапишет ошибку WriteString» — нет: Close
записывается, только если запись прошла. «Ошибка разбора списка PR —
дальше цикл с пустым списком» — так и задумано: пустой список ничего
не делает. Проверка секретов честно ловит ключ-образец в тесте, специально
написанный для неё, — это ожидаемое срабатывание, не ошибка. Поэтому
вердикт — комментарий, а мёржит человек.

## Код

| файл | что там |
|---|---|
| `internal/review/diff.go` | разбор unified diff: файлы, статусы, строки хунков |
| `internal/review/checks.go` | проверки кодом |
| `internal/review/review.go` | пайплайн: RAG, попытки, запасная модель, сверка ответа |
| `internal/review/prompt.go` | промпт ревьюера и markdown отчёта |
| `internal/review/metrics.go` | журнал прогонов, p50/p95, цена, алерт |
| `cmd/advent/day32.go` | `advent review`: `-pr`, `-base`, `-watch`, `-max-reviews`, `-comment`, `-stats` |
| `docs/REVIEW.md` | правила ревью проекта — источник для RAG |

## Запуск

```powershell
$env:LLAMA_CPP_DIR = 'C:\Users\sanya\tools\llama'
.\scripts\rag-servers.ps1
go build -o advent.exe ./cmd/advent
.\advent.exe index -base review -strategy structure
.\advent.exe review -base day-31                 # ветка без PR, отчёт в reports/review/
.\advent.exe review -pr 32 -comment              # один PR
.\advent.exe review -watch 30s                   # наблюдатель: каждый новый PR и коммит
.\advent.exe review -stats                       # метрики
```

## Запись демо

PR «Day 31» должен быть открыт заранее, PR «Day 32» открывается во время
записи (через минуту после старта), и наблюдатель подхватывает его сам.

```powershell
.\scripts\demo.ps1 -Name day32 -MaxSeconds 900 -AppArgsList @(
  @('review','-watch','15s','-max-reviews','2'),
  @('review','-pr','33','-model','deepseek-broken','-comment','-hold','8s'),
  @('review','-stats','-hold','12s'))
```
