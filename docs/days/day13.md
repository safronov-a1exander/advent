# День 13 — состояние задачи (Task State Machine)

Ветка: `day-13` (от `day-12`)

## Что добавляет этот шаг

До сих пор разговор был плоским. Память (день 11) знала, **что известно**,
профиль (день 12) — **как отвечать**, но ничто не знало, **где мы сейчас**:
собираем требования, пишем код или проверяем сделанное. Из-за этого агент
с одинаковой готовностью пишет реализацию на второй реплике и переспрашивает
про требования на десятой.

Тринадцатый день добавляет задачу с явным состоянием:

```
planning → execution → validation → done
```

Четыре стадии — не выбор, а совет курса: эти четыре не трогать, расширять
уже внутри них. Состояние — обычные данные:

```go
type Task struct {
    State   State     // этап конечного автомата
    Step    int       // текущий шаг
    Plan    []string  // утверждённый план
    Done    []string  // что уже сделано
    Current string    // что делаем сейчас
    Expect  string    // ожидаемое действие
    Log     []Event   // журнал переходов
}
```

Оно лежит в `tasks/<задача>.json`, уходит в промпт блоком и переживает
закрытое приложение. Задача и рабочий слой памяти дня 11 делят один
идентификатор: это одна и та же задача с двух сторон — состояние отвечает
«где мы в ней», рабочая память «что мы в ней выяснили».

### Блок в промпте

Формат взят со слайда лекции почти дословно — помеченные блоки читаются
моделью лучше связного абзаца и, что важнее, видны глазами в журнале
запросов, когда разбираешься, почему агент повёл себя не так:

```
[ЗАДАЧА]  Telegram-бот записи в барбершоп
[СТАДИЯ]  execution (выполнение), шаг 3 из 6
[ЦЕЛЬ]    выполнять утверждённый план по шагам…
[СЕЙЧАС]  интеграция с Google Calendar
[ПЛАН]
  ✓ 1. Требования и модель данных
  ✓ 2. Схема базы
  → 3. Интеграция с Google Calendar
    4. Telegram-бот
[СДЕЛАНО]
  - схема базы готова, миграции накатаны
[ЖДЁМ]    подтвердить формат слотов

Правила:
- работай только в рамках текущей стадии и текущего шага;
- не перепрыгивай стадии…
```

Порядок блоков в системном промпте теперь такой:

```
system → профиль → дорога → ЗАДАЧА → память → [сводка/факты] → история
```

Задача перед памятью: она задаёт рамку, память её наполняет.

### Кто двигает состояние

- `manual` — состояние в промпте, двигает пользователь: `/stage execution
  план одобрен`, `/step схема готова`. Служебных вызовов нет.
- `auto` — плюс служебный вызов после каждого ответа. Он смотрит на пару
  «вопрос–ответ» и возвращает **разницу**: закончилась ли стадия, лёг ли
  план, закрыт ли шаг. Обычный ход даёт `{}`.

Вызов идёт **после** ответа, но **до** записи хода в учёт: раньше нельзя —
пока ответа нет, непонятно, закончилась ли стадия; позже нельзя — токены
служебного вызова потерялись бы между ответом и ходом.

Почему отдельный вызов, а не маркер в ответе: разметка вида «закончи ответ
строкой STEP_DONE» ломается ровно тогда, когда ломается всё остальное —
модель увлеклась и забыла маркер.

Важно: вызов **предлагает**, а не приказывает. Куда задаче можно перейти,
решает код (`task.Allow`). На тринадцатом дне это движение строго вперёд
и только на следующую стадию; на пятнадцатом станет картой с откатами
и запретами.

### В интерфейсе

- В шапке — `◆ execution 3/6 · интеграция с Google Calendar`.
- `/stage` без аргумента показывает, на чём остановились; `/stage
  execution план одобрен` переводит стадию; `/step схема готова` закрывает шаг.
- `Ctrl+D` печатает «на чём остановились» и план с отметками.
- Служебный вызов виден в ленте, как раскладка памяти дня 11, и считается
  в колонке «служеб» в `Ctrl+T`.
- `Ctrl+R` стирает переписку, но **не** задачу: стёртая переписка не значит,
  что работа не сделана.

### Снаружи приложения

```bash
go run ./cmd/advent task                       # где какая задача стоит
go run ./cmd/advent task -show бот             # стадия, план, сделано, журнал
go run ./cmd/advent task -show бот -stage execution -note "план одобрен"
go run ./cmd/advent task -show бот -step "схема готова"
```

Проверка допустимости перехода тут та же, что у агента: снаружи можно
не больше, чем изнутри, иначе «нельзя перепрыгнуть этап» обходилось бы
одной командой.

## Сравнение: `advent dialog` с обрывом разговора


Три варианта: без стадий, со стадиями, и со стадиями плюс sliding window
с хвостом 2. Третий — главный: модель почти не видит переписки, всё, что
она знает о задаче, приходит из блока состояния.

Посередине `newchat` — разговор оборван, как будто пользователь закрыл
приложение и вернулся назавтра. Последняя реплика — попытка объявить
задачу закрытой без проверки.

## Проверено на живом API

`deepseek-flash`, `thinking: disabled`, `temperature: 0`, три прогона.

| вариант | вход | из кэша | служебные | выход | проверки, прогоны 1 · 2 · 3 | $ |
|---|---:|---:|---:|---:|---|---:|
| без стадий | 4 043 | 57% | 0 | 1 170 | 2/5 · 2/5 · 2/5 | 0.00194 |
| стадии, агент | 16 063 | 4% | 8 184 | 2 260 | **5/5 · 5/5 · 5/5** | 0.00402 |
| стадии + окно 2 | 14 835 | 9% | 8 838 | 2 469 | 4/5 · **5/5 · 5/5** | 0.00304 |

Объёмы — из второго прогона.

### Что видно

- **Две проверки до обрыва проходят все, три после — только стадии.**
  Вариант без стадий на «на чём мы остановились» отвечает честно: «истории
  у меня перед глазами не сохранилось, скинь, пожалуйста: что за задача,
  что уже сделано, где затык». Это ровно то, чего задание просило избежать —
  повторные объяснения.
- **Окно 2 работает почти как полная история.** Модель видит два последних
  сообщения, но знает стадию, план и что сделано, потому что это приходит
  блоком состояния. Состояние действительно заменяет пересказ «а мы тут
  вот что решили» — и стоит на 25% дешевле полной истории со стадиями.
- **Служебный вызов — половина входа** (8 184 из 16 063), как и раскладка
  памяти на одиннадцатом дне. Выход при этом скромный: разница, а не всё
  состояние целиком.
- **Кэш почти не работает** — 4%. Блок состояния меняется каждый ход:
  шаг, «сейчас», «ждём». Это дороже, чем память (26% на дне 11), и тут
  ничего не поделать: состояние на то и состояние.
- **Прыжок через стадию не проходит.** На «считай задачу завершённой прямо
  сейчас, без проверки» задача осталась в `execution`: переход
  `execution → done` не разрешён кодом. Уговаривать нечего — это не промпт,
  это `Allow`.

### Что оказалось хрупким

- **Счётчик шагов дрейфует, если служебный вызов щедр на «сделано».**
  В первом прогоне к концу разговора стояло «шаг 6 из 6, сделано 5», хотя
  пользователь отчитался о трёх пунктах: вызов считал «сделанным» и то, что
  просто обсудили. Помогла одна строка в инструкции — «обсуждение пункта
  и планы его сделать это не „сделано“; каждое лишнее completed двигает
  счётчик вперёд реальной работы». После правки — «шаг 4 из 6, сделано 3».
  Стадия и план устойчивее счётчика: они меняются редко и по явному поводу.
- **План, пойманный при узком окне, может быть до правки.** В одном прогоне
  вариант с окном 2 сохранил план из пяти пунктов, хотя шестой был добавлен
  в той же реплике, что и утверждение. Служебный вызов видит состояние и
  последнюю пару — если правка и утверждение пришли вместе, поймать можно
  предыдущую версию.
